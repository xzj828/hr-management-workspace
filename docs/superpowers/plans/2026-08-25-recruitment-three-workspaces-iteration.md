# 招聘三工作区与管理入口迭代计划

> 日期：2026-08-25
> 状态：Iteration 1 已完成并通过统一验收；模型切换作为后续独立迭代
> 范围：兼容式前端重组；复用现有招聘领域 API 与安全运行时

## 目标

把招聘产品从六个技术对象页面重组为三个用户意图工作区：

1. 招聘作业台：上传岗位依据、填写要求、设置方案/数量并执行。
2. 结果中心：集中查看运行、人工介入、候选人、简历/评分和阶段结果。
3. 管理后台：集中职位同步、BOSS 账号/隔离浏览器、流程编排、模型和诊断。

## 验收标准

- HR 从进入招聘模块到创建主动寻访任务，全程不离开作业台。
- 作业台同屏包含岗位、账号、依据文件、文字要求、方案、数量、执行前检查和唯一主动作。
- 任何阻塞条件都显示业务可读原因与解决入口，不出现“点击无反应”。
- 执行成功后立即给出运行标识、状态与结果中心链接；刷新结果中心可恢复运行。
- 运行、人工介入、候选人、简历/评分、失败原因和阶段结果均能从结果中心进入。
- 职位同步、BOSS 账号/浏览器、流程编排、模型和诊断不再占用 HR 主业务页面。
- 旧 URL 保留 `job/run/filter` 上下文并定向到正确的新工作区。
- 现有业务模型、文件版本、审计历史和 RPA 安全门不被复制、丢失或绕过。

## 风险与回退

- 多资源加载必须使用岗位/运行请求序号，避免快速切换时旧响应覆盖新上下文。
- 第一轮沿用创建标准流程 → 启用版本 → 正式运行的既有 API；提交过程逐步报告错误且禁止双击。后续再评估原子招聘作业端点。
- 旧页面组件继续保留为兼容和回退路径；导航重组不删除数据或迁移数据库。
- 若某结果类型无法安全聚合，结果中心提供明确的内嵌摘要和上下文深链，不伪造完成状态。

## API 与数据模型记录

原计划不新增 API、字段、模型或依赖。第一轮对抗审查证明既有 RPA 能力声明与执行路径没有完整落实 `autodev-rules.md` 的审批、额度和身份复核红线，因此允许在不改变产品目标的前提下收紧既有服务端契约，并同步 `autodev-api.md`；若修复需要迁移，将以最小字段/约束和可回滚迁移实施。

## 第一轮对抗审查记录

- 结论：FAIL（功能 4/10、健壮性 4/10、最小改动 5/10、代码质量 6/10）。
- P0：被动 `request_resume` 无人工确认且 Worker 仅凭姓名执行；主动 `search_pull_resumes` 把多次在线简历打开记为一次搜索。
- P1：成功后可重复创建运行；结果中心把既有详情和操作重定向为摘要；旧 URL 上下文只保留字符串但未恢复业务状态；管理入口未按角色收敛。
- 修复策略：先收紧服务端安全门，再恢复隐藏详情页/内嵌详情和提交幂等，完成定向与全量回归后交由未参与修复的 reviewer 重新评分。

## 第二轮对抗审查记录

- 结论：FAIL（功能 6/10、健壮性 3/10、最小改动 6/10、代码质量 6/10）。
- 已通过项：approval 编排、结果处理、旧链接、run-only 岗位恢复、提交恢复、自定义流程、角色与浏览器反馈。
- 阻断项：索简历仍以会话姓名唯一替代稳定身份；主动批量只有预算预扣、没有逐份持久化证据；批量回写异常可能提交部分业务副作用并让 Task 缺少终态。
- 修复策略：稳定身份不可取得时 fail closed；增加任务级逐次证据和预算/实际账；把批量业务回写与失败终态拆成“内层全回滚、外层落失败”的事务边界，并用故障注入测试证明。

## 第三至第五轮对抗审查与收口

- 第三轮：关闭空平台 ID 回写、通用批准任务重复创建/取消、证据 PII 和批量事务半提交旁路。
- 第四轮：补齐工作流 `deep_search` 的确认与专用物化、主动寻访取消后的工作流终结、暂停任务不支持假续跑，以及全部 Worker 回写终态的额度账本。
- 第五轮：补齐 Worker 租约超时这一最后的领域终态旁路；Task、Campaign、脱敏额度证据、账号状态和 Workflow 统一失败收口。
- 第五轮子审计：补齐 Workflow 取消后的审批/租约门禁、Campaign 直接停止的节点同步、`deep_search` 按 attempt 重试，并统一过期确认与 superuser 服务契约。
- 最终限制：生产 BOSS CLI 尚无按平台稳定 ID 原子执行接口，相关外部动作会安全转人工；主动寻访预留额度不退款；暂停中的 Campaign 需新建任务。

- 红线：未发现占位核心实现、Mock 替代真实接口、emoji 功能图标或设计降阶；当前下一阶段文案均为明确产品决策且没有假交互。
