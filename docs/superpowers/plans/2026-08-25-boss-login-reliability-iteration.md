# BOSS 隔离浏览器与登录可靠性迭代

> 日期：2026-08-25  
> 状态：已完成  
> 范围：隔离浏览器启动、Worker 就绪、登录状态与管理后台反馈；不改变外发审批和身份核验边界

## 根因

- 当前开发运行只启动 Vite 与 Django，未启动 RPA Worker，两个打开登录任务长期停在 `pending`。
- Worker 离线时前端仍允许排队，管理后台不自动轮询，用户无法看到任务收敛。
- Windows 全局 `boss.CMD` 由命令解释器处理，业务 argv 存在 shell 元字符注入风险。
- Worker 在线状态可能陈旧；普通 BOSS 页面可能被误判为已登录；等价登录任务可以重复创建。

## 方案

- [x] 将 boss-cli 调用固定为可信 `node.exe + CLI JavaScript 入口`，拒绝脚本 shim，并最小化子进程环境。
- [x] Worker 即使 CLI 不可用也上报结构化心跳；网络抖动时退避恢复，不永久假在线。
- [x] 同账号等价打开登录任务在服务端锁内复用，Worker/CLI 不可用时不新增永久排队任务。
- [x] 收紧 BOSS `ready` 判定，公共页、错误页、未知页面失败关闭。
- [x] 管理后台增加 Worker/CLI 前置阻塞、账号内任务阶段和 5 秒非重叠轮询。
- [x] POST 成功与刷新失败分离；登录窗口已打开时任务成功、账号保持等待扫码，风控才进入人工处理。
- [x] 增加 Windows CLI 注入、重复任务、心跳 TTL、状态误判、前端轮询与不确定提交回归。
- [x] 启动本机 RPA Worker，验证排队任务收敛并实际打开两个受管 Edge 登录窗口。

## 验收标准

- Worker 离线时点击不会产生新的永久 `pending`，页面明确说明恢复动作。
- Worker 在线后，打开登录窗口在账号上下文中显示阶段，并在 5 秒内自动反映状态变化。
- 同账号跨标签重复提交只得到同一活动任务。
- 任意 HR 输入不能经 npm shim 进入 `cmd.exe` 解释；子进程不继承 Worker Token 等部署秘密。
- 公共首页、错误页或错误 CDP 实例不能开放职位同步或正式执行。
- 不保存 BOSS 密码，不绕过扫码、验证码、App 确认或风控。

## 回退

保留现有 RPA 任务模型和端点；若 CLI 固定入口在某部署不可发现，Worker 以 `cli_available=false` 在线上报并阻塞业务动作，不回退到执行 `.cmd` shim。
