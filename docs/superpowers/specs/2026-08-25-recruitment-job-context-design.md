# 招聘岗位上下文与全局看板重构设计

状态：用户已确认

## 背景

当前招聘模块按页面组织职位、候选人、流程、自动化和简历，但候选人、应聘记录与简历默认混合展示多个职位的数据。HR 在页面间切换时缺少持续、明确的岗位上下文，容易查看或操作错误的职位。招聘看板虽然展示全局数据，却没有承担从全局发现问题并下钻到具体岗位的职责。

本次重构将招聘模块分成“全局指挥中心”和“岗位工作区”两层。招聘看板、职位管理和自动化任务保持全局视角；候选人、招聘流程和简历中心必须在明确选择一个在招职位后工作。

## 目标

1. 顶部导航提供唯一的岗位切换入口，避免页面内重复选择职位。
2. 候选人、流程和简历按当前职位严格隔离，后端同时执行权限与数据范围校验。
3. 招聘看板成为全部在招职位的全局指挥中心，并支持一键下钻到岗位工作区。
4. 职位选择在刷新、跨页面和再次登录后可恢复，但职位关闭、归档或无权限时自动失效。
5. 保留现有职位同步、自动化安全边界、人工确认和审计能力。

## 非目标

- 不改为职位嵌套路由，不新增 `/recruitment/jobs/<id>/...` 路由体系。
- 不在进入招聘模块时自动调用 BOSS 同步；职位数据仍由“职位管理”的同步按钮更新。
- 不让当前职位筛选招聘看板、职位管理或自动化任务。
- 不在本次实现简历 AI 评分、Copilot 或新的 BOSS 写操作。
- 不把前端过滤作为安全边界。

## 信息架构

### 全局页面

- 招聘看板 `/recruitment`
- 职位管理 `/recruitment/jobs`
- 自动化任务 `/recruitment/automation`

这三个页面展示“全部职位 · 全局视图”，不受当前职位筛选影响。系统保留用户最后选择的职位，但全局页面 URL 不携带 `job` 参数。

### 岗位工作区页面

- 候选人 `/recruitment/candidates?job=<id>`
- 招聘流程 `/recruitment/pipeline?job=<id>`
- 简历中心 `/recruitment/resumes?job=<id>`

这三个页面必须存在合法、在招且当前用户可访问的职位。未选择职位时不请求混合业务数据，只显示岗位选择引导。

## 方案决策

采用“URL 查询参数 + Pinia 全局状态 + 后端强制筛选”。

- URL 是可复制、可前进后退的页面上下文。
- Pinia 负责职位列表、选择状态、失效处理和跨页面同步。
- 按登录账号持久化最后选择的职位，支持刷新和再次登录恢复。
- 后端按职位与当前用户权限筛选，防止前端遗漏或手工修改 URL 导致跨职位、跨账号读取。

未采用纯前端过滤，因为它会返回不必要的数据并容易因页面遗漏重新混岗。未采用职位嵌套路由，因为当前收益不足以覆盖路由、跳转和测试的整体迁移成本。

## 前端架构

### Recruitment Context Store

新增独立的 `recruitmentContext` store，职责限定为：

1. 加载当前用户可访问、未归档且状态为 `open` 的职位。
2. 解析并校验路由中的 `job`。
3. 保存当前职位并同步到岗位页面 URL。
4. 以登录用户 ID 为命名空间保存最后选择的职位。
5. 在同步完成、职位关闭、归档或权限变化时重新校验当前选择。

选择优先级：

1. URL 中的合法职位；
2. 当前用户最后一次合法选择；
3. 无选择状态。

不得自动选择职位列表第一项，以免 HR 未注意上下文便开始操作。

### 路由与导航

岗位页面之间跳转时持续携带当前 `job`。进入全局页面时移除 URL 的 `job`，但不清除 store 和持久化记忆。重新进入岗位页面时恢复最后有效选择。

顶部职位上下文区位于模块内导航右侧、Copilot 左侧：

- 岗位页面：可搜索的职位下拉框。
- 全局页面：不可点击的“全部职位 · 全局视图”标识。
- 下拉项显示职位名称、部门和 BOSS 账号；同名职位仍可辨认。
- 切换完成后短暂反馈“已切换到 <职位名称>”。
- 长名称省略但保留悬停完整文本，支持键盘操作。

顶部选择器是岗位工作区唯一的职位切换入口。候选人发现等页面内原有职位选择器删除，或改为不可编辑的当前岗位摘要。

### 请求一致性

岗位页面只有在职位上下文完成校验后才发送业务请求。所有请求显式携带 `job`。快速切换职位时取消或忽略旧请求，响应落库前再次核对请求对应的职位，防止旧数据覆盖新页面。

## 后端数据边界

### 职位校验

所有岗位级接口共享同一职位解析规则：职位存在、未归档、状态为 `open`，并且当前用户通过职位所属 BOSS 账号授权或职位 owner 获得访问权。超级管理员仍按既有规则访问全部职位。

非法 ID 返回 400；不存在或不可访问的职位按统一策略返回 404，避免暴露其他账号的职位存在性；已关闭或归档的职位返回可识别的业务错误供前端清除上下文。

### 应聘记录作为岗位工作单元

岗位工作区的主业务对象由 Candidate 改为 JobApplication：

- 同一 Candidate 可同时拥有多个职位的 JobApplication。
- 阶段、负责人、来源、互动时间、沟通、面试和职位级简历均绑定对应 JobApplication。
- 在一个职位淘汰、移出或归档应聘记录，不影响该候选人在其他职位的应聘记录。
- Candidate 继续保存共享的姓名、联系方式和当前经历，避免重复建档。

候选人详情以当前 JobApplication 为主，其他职位的应聘记录仅在次级折叠区只读展示，并继续受用户权限约束。

### 接口调整

- `GET /api/recruitment/jobs/?status=open`：为顶部选择器返回可访问的在招职位。
- `GET /api/recruitment/applications/?job=<id>`：岗位候选人列表与流程的主数据源。
- `GET /api/recruitment/candidates/?job=<id>`：若保留使用，只返回该职位关联人员，并限制序列化的应聘记录范围。
- `GET /api/recruitment/resumes/?job=<id>`：仅返回该职位 JobApplication 关联的简历。
- 候选发现、沟通批次、在线简历保存和面试邀约请求继续传递职位或 JobApplication，并在服务端交叉校验。

当前 `JobApplicationViewSet` 缺少完整的用户数据范围校验，Candidate 序列化也会携带当前用户可见范围内的其他职位应聘记录；这两个问题必须在本次一并修正。岗位隔离既是产品行为，也是权限边界。

## 页面设计

### 招聘看板

招聘看板固定为全局指挥中心，不增加顶部职位筛选。

页面顺序：

1. “全部在招职位”整体 KPI。
2. 今日待处理：待联系、待筛选、待面试、人工确认和自动化失败。
3. 在招职位概览。
4. 全局招聘漏斗与趋势。
5. 自动化风险与最近活动。

每个职位卡片展示招聘目标与进度、候选人数、待筛选数、待面试数、最近更新时间、BOSS 账号状态和风险提示。点击卡片跳转到 `/recruitment/candidates?job=<id>` 并建立岗位上下文。

没有同步职位时不渲染无意义的空图表，显示单一入口“前往职位管理同步职位”。看板统计始终不受 store 中最后选择职位的影响。

### 候选人

- 列表以 JobApplication 为行，显示候选人、阶段、来源、负责人、最近互动和简历状态。
- 搜索、推荐、深度匹配、加入候选人库和创建沟通动作自动绑定当前职位。
- 详情主区域只展示当前职位应聘信息，其他应聘职位进入次级折叠区。
- 当前职位的淘汰、移出或归档不影响其他职位。
- 空态只提供“发现候选人”这一主要下一步。

### 招聘流程

- 只加载当前职位的 JobApplication。
- 顶部展示职位目标、候选人数和关键待办。
- 阶段拖动后继续要求确认原因并记录审计历史。
- 空态提供“前往候选人发现”。

### 简历中心

- 只展示当前职位 JobApplication 关联的 PDF。
- 详情明确显示候选人和应聘职位。
- 保留预览、下载、归档和历史版本。
- 智能初筛继续作为下一阶段禁用入口；未来评分必须绑定 Candidate + JobApplication，不生成脱离职位的通用分数。

### 职位管理与同步

同步按钮继续创建现有异步只读同步任务。只有任务成功并将完整结果写入数据库后，recruitment context 才重新加载职位列表。同步失败保留旧列表，不清空、不展示半成品。

如果同步结果使当前职位关闭、归档或消失，岗位页面退出当前上下文，说明原因并要求重新选择。职位选择器展示最近一次成功同步时间，并在数据较旧时提示前往职位管理同步，但不自行调用 BOSS。

### 自动化任务

保持全局视角，因为账号、同步任务、确认批次和流程版本本身就是跨职位管理对象。创建正式流程运行时仍显式选择或校验目标职位，不隐式采用 store 中的最后职位。

## 状态与错误处理

### 加载中

顶部选择器和当前内容使用局部骨架。切换职位不清空整个应用壳，不显示整页白屏。

### 未选择职位

岗位页面不请求业务列表，展示职位选择引导。没有在招职位时引导去职位管理同步。

### 无数据

分别说明“该职位暂无候选人”“暂无流程记录”“暂无简历”，每个页面只保留一个最合适的下一步。

### 职位失效

清除 URL 和持久化选择，保留页面壳，显示职位已关闭、归档或不可访问，并提供重新选择。

### 请求失败

保留当前职位和已成功加载的数据，显示局部错误与重试。未经成功响应不得切换成空数据状态。

## 动效与可访问性

- 下拉展开、内容切换和状态反馈使用 150–220ms 动效。
- 尊重 `prefers-reduced-motion`。
- 下拉框支持键盘导航、Escape 关闭、明确焦点样式和可读标签。
- 职位切换只更新受影响内容，不闪烁整个页面。
- 危险动作继续使用明确确认，不新增无说明的直接删除。

## 测试策略

### 后端

- 在招职位列表只返回当前用户可访问数据。
- `job` 缺失、非法、不存在、关闭、归档和无权限的行为一致。
- JobApplication、Candidate 和 Resume 按职位隔离。
- 同一 Candidate 对应两个职位时，各自阶段、简历和操作不串联。
- 手工修改 URL 不能读取未授权职位。
- 同步失败不破坏既有职位列表，同步成功后关闭职位会使上下文失效。

### 前端

- URL 优先、持久化恢复和按用户隔离。
- 三个岗位页面请求始终携带当前 `job`。
- 三个全局页面不受当前职位影响。
- 岗位页面之间切换保留职位，全局页面 URL 不携带职位。
- 未选择职位时不请求混合业务数据。
- 快速切换职位时旧响应不能覆盖新职位。
- 同步任务成功后刷新下拉列表，失败时保留原列表。
- 看板职位卡正确下钻并建立上下文。

### 浏览器验收

按以下路径完成真实浏览器验收：

1. 职位管理同步职位。
2. 选择一个在招职位。
3. 查看候选人、招聘流程和简历中心，确认数据口径一致。
4. 切换另一个职位，确认无旧数据闪回或混入。
5. 返回招聘看板，确认仍展示全局数据。
6. 点击职位卡片重新进入岗位工作区。
7. 刷新、退出并重新登录，确认合法选择可恢复。
8. 关闭或归档当前职位，确认上下文安全失效。

## 完成标准

- 岗位页面在没有合法职位上下文时不会展示全部职位数据。
- 同一职位在候选人、流程和简历中的数量与对象关系一致。
- 全局页面与岗位页面的视觉标识清楚，用户不会误认为全局页面已被筛选。
- 职位同步、选择、下钻、失效和恢复形成完整操作闭环。
- 数据权限测试、前端回归测试、生产构建和浏览器主流程验收全部通过。
