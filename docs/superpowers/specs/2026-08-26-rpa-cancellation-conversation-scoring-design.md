# RPA 取消、消息筛选与重点评分设计

日期：2026-08-26

## 目标

本次改动解决三个相互关联的招聘自动化问题：

1. 用户取消任务后，正在执行的自动化必须尽快停止，不再操作、切换或唤起隔离浏览器；浏览器本身和登录状态继续保留。
2. 被动消息流程只处理当前所选职位下的未读会话，不能遍历所有聊天框。
3. 核心要求、硬性要求等都不是淘汰门槛，只作为权重较高的评分项。

## 非目标

- 取消任务时不关闭隔离浏览器，也不清除账号登录数据。
- 不对岗位名称不明、候选人身份不唯一的会话进行猜测性操作。
- 不允许 AI 评分自动推进或淘汰候选人。

## 方案选择

采用“服务端取消请求 + Worker 主动中断子进程”的方案。

只在自动化步骤之间检查任务状态实现简单，但单条 boss-cli 命令可能持续数分钟，用户取消后浏览器仍会继续动作，因此不能满足需求。关闭整个浏览器虽然能强行停止，却会干扰用户并破坏保留登录窗口的要求。

## 一、任务可中断取消

### 状态流转

- `pending` 任务取消后直接进入 `cancelled`。
- `leased` 或 `running` 任务取消后先进入 `cancel_requested`，前端显示“正在取消”。
- Worker 确认自动化命令已停止后，将任务变为 `cancelled`。
- 已进入终态的任务重复取消保持幂等，不重新执行任何动作。

通用任务、工作流沟通任务和主动寻访任务使用同一套取消语义。上层的工作流、批次或寻访活动等待 Worker 的取消回执后再收敛到取消状态，不能只改上层状态而放任底层命令继续运行。

### Worker 与进程控制

- boss-cli 普通命令从阻塞式 `subprocess.run` 改为可监控的 `Popen` 执行。
- Worker 执行期间短间隔查询任务控制状态；收到 `cancel_requested` 后终止当前 boss-cli 进程并等待退出，必要时再强制结束该命令进程。
- 只停止本次命令进程，不结束已登录的 Edge/Chrome 隔离浏览器。
- Windows 下隐藏 boss-cli 自身的控制台窗口，避免额外窗口抢占前台。
- 每个可能循环操作多名候选人的执行器也在循环边界检查取消，保证不会在一条命令结束后继续下一个人。

### 完成回执保护

- 服务端收到已请求取消任务的普通成功/失败回执时，不得把任务覆盖回成功或失败。
- Worker 发送明确的取消回执，审计事件记录取消请求时间、实际停止时间和 Worker。
- 取消后账号回到可用状态；浏览器仍保持原登录状态。

## 二、仅处理所选职位的未读会话

### 列表预筛选

- 同步消息时调用 boss-cli 的未读列表能力，即 `list --unread`。
- 会话列表解析器保留候选人名称、未读状态、岗位名称、稳定身份字段和消息摘要。
- 在打开聊天框之前，按以下条件依次筛选：
  1. 会话确实为未读；
  2. 会话岗位名称与任务中冻结的所选岗位名称一致；
  3. 候选人在该账号、该职位下可以唯一对应到一条投递记录。
- 岗位名称只做空白字符归一化后精确比较，不做模糊猜测，避免相似职位串单。
- 岗位缺失、岗位不符、同名歧义或身份不一致时跳过会话并记录原因，不打开聊天框。

### 打开与入库

- 最多处理 50 条“已经通过预筛选”的会话，而不是列表中的前 50 条全部会话。
- 只有通过预筛选的会话才允许调用 `chat --strict`、读取消息和下载简历附件。
- 服务端入库时再次使用任务冻结的岗位 ID 校验投递记录，形成 Worker 和服务端两层防护。
- 只有本轮符合条件的未读消息才触发意图识别；只有意图识别认为需要索要简历时，才进入既有的人工确认/索要简历流程。
- 已读会话、其他岗位会话不能触发索要简历。

## 三、核心/硬性要求改为重点评分项

### 统一业务含义

- 页面不再把相关要求称为“硬性指标”“淘汰条件”或 “HARD GATES”，统一称为“重点评分项”。
- 核心要求、重点评分项、学历、经验、技能、城市等条件即使明确不满足，也只影响得分。
- 删除“明确不满足时自动淘汰”开关和相关提示。
- 评分结果不再因为重点项未满足而强制改成 `hold`，也不再自动改变候选人阶段。

### 权重与兼容

- 新生成的评分标准把重点项作为普通评分维度的一部分，但默认权重高于普通项；所有维度最终仍归一化为总计 100 分。
- 重点项的默认相对权重为普通项平均权重的 `2` 倍；HR 仍可在发布前手工调整各项权重。
- 主动寻访中填写的核心要求只进入后续评分依据，不作为本系统的强制淘汰条件。
- 历史标准中的 `hard_requirements` 字段继续可读。评分时将其适配为重点评分项；`auto_reject_on_hard_fail` 即使历史值为 `true` 也不再执行淘汰。
- 历史评估记录保留原字段用于审计，新评估只记录“重点项差距”，前端不再展示为淘汰结果。

## 错误与人工处理

- 取消超时：任务保持“正在取消”，记录错误并提示 Worker 状态，不把它伪装成已取消。
- 会话岗位缺失或身份歧义：安全跳过并记录同步原因，不弹出聊天窗口。
- boss-cli 不支持未读参数或输出无法解析：本次同步失败并给出明确提示，不回退到遍历全部会话。
- 评分资料不足：相应维度不得分或低置信度，交由 HR 复核，但不自动淘汰。

## 测试范围

- 任务状态：待执行取消、运行中取消、重复取消、取消后晚到成功回执、工作流/寻访状态收敛。
- Worker：运行命令收到取消后终止、浏览器进程不被关闭、循环执行器停止后不处理下一人。
- 会话：只调用未读列表、解析岗位、岗位精确匹配、其他岗位不打开、同名歧义不打开、服务端按岗位二次校验。
- 流程：只有匹配岗位的未读消息能够触发后续索要简历逻辑。
- 评分：重点项未满足只扣分、不改为暂缓、不自动淘汰；历史标准兼容；前端不再出现硬淘汰开关和文案。

## 验收标准

1. 运行中的任务点击取消后，当前自动化命令停止，浏览器保留但不再继续跳动或弹出。
2. 一个账号存在已读、其他岗位未读、目标岗位未读三类会话时，只打开目标岗位的未读会话。
3. 候选人明确不满足任一重点项时仍产生正常总分和建议，不自动改变招聘阶段。
