# 招聘第三阶段：岗位标准与简历智能初筛设计

日期：2026-08-25  
状态：已确认，待实施

## 1. 目标

第三阶段在现有职位、岗位 Word 文档、候选人和简历归档能力之上，建立可追溯的简历智能初筛链路：

1. 本地解析岗位 Word 文档。
2. 使用大模型生成可编辑的评分标准草稿。
3. 本地提取 PDF、扫描 PDF 和 PNG 在线简历内容，并使用大模型完成结构化。
4. 在 HR 发布评分标准后，对简历生成分数、证据和筛选建议。

评分规则暂未最终确定，因此系统不得内置一套看似正式的通用规则。未发布评分标准时，简历只完成结构化，不产生正式分数。

## 2. 已确认决策

- 使用混合解析架构：本地程序负责读取文件，大模型负责理解和结构化文字。
- 原始 Word、PDF 和 PNG 文件继续保存在本地，不把整个文件直接发送给模型服务。
- 模型统一通过 OpenAI 兼容协议调用，配置包含 API 地址、模型名称和 API Key。
- 模型配置按当前登录账号保存；API Key 沿用现有加密存储，只在服务端解密使用，不返回前端。
- Word 和简历入库后自动处理，同时提供失败原因、手动重试和历史版本。
- PDF 附件简历和 BOSS PNG 在线简历使用同一套结构化简历模型。
- 大模型只能提供 HR 决策辅助，不自动淘汰候选人或改变候选人流程状态。
- 性别、民族、婚育等敏感属性不得作为评分依据。

## 3. 非目标

- 本阶段不实现面试邀约或复杂自动对话。
- 本阶段不自动发布或修改 BOSS 职位。
- 本阶段不根据未确认的建议规则生成正式分数。
- 本阶段不让模型直接决定候选人的录用、淘汰或流程推进。
- 本阶段不建设独立的向量数据库、知识库平台或复杂消息中间件。

## 4. 总体架构

系统划分为五个边界清晰的模块。

### 4.1 文件提取层

文件提取层只负责把本地文件转换为可定位的文字片段，不理解招聘语义。

- DOCX：提取标题、段落、表格、列表及其顺序。
- DOC：通过本机 LibreOffice 转换为 DOCX 后解析；没有转换能力时保留文件并提示用户另存为 DOCX。
- 文字型 PDF：提取分页文字和文字块位置。
- 扫描 PDF：当提取文字过少或质量不达标时，逐页转图后进入本地 OCR。
- PNG 在线简历：进入本地 OCR，并保留文字块与图片区域的对应关系。

提取结果保存为本地中间数据，包含页码或文档区块定位。后续模型失败时可复用该结果，不重复执行 OCR。

### 4.2 大模型网关

大模型网关是唯一允许访问外部模型服务的模块，向业务代码提供稳定接口：

- `test_connection`：测试配置是否可用。
- `structure_job_standard`：把岗位文档文字整理成标准草稿。
- `structure_resume`：把简历文字整理成统一结构。
- `score_resume`：按照已发布标准生成评分、证据和建议。

网关统一使用 OpenAI 兼容协议。业务模块不得依赖某个厂商专属的请求或响应格式。所有响应都必须通过固定 JSON Schema 校验后才能入库。

### 4.3 版本化业务数据

新增三类版本化结果：

- 岗位标准版本：绑定职位、岗位文档版本和生成时使用的模型。
- 结构化简历版本：绑定简历文件版本和生成时使用的模型。
- 简历评分版本：绑定不可变的岗位标准版本与结构化简历版本。

上传新文件、修改标准或重新评分都创建新版本，不覆盖历史结果。任何评分必须能追溯到原始文件、标准版本、结构化版本、模型和时间。

### 4.4 后台处理内核

解析和评分通过数据库任务运行，不阻塞上传接口。任务状态为：

- 等待模型配置
- 等待处理
- 文本提取中
- OCR 处理中
- 模型处理中
- 待人工确认
- 已完成
- 失败

任务具有明确的阶段、进度、尝试次数、错误代码和错误摘要。使用幂等键避免重复上传或重复点击产生重复结果。首版复用项目现有后台 Worker 与数据库调度方式，不引入 Redis、Celery 等额外基础设施。

### 4.5 招聘界面

主要入口位于简历中心，并与当前职位上下文一致。招聘看板只展示汇总和跳转，不承载复杂编辑。

## 5. 岗位 Word 与评分标准

### 5.1 处理流程

`上传并绑定职位 → 本地提取 → 模型生成草稿 → HR 编辑 → 校验 → 发布`

Word 文档仍沿用现有职位绑定和文件版本。多个用户画像、招聘需求或其他标准文档可以共同生成一个岗位标准草稿。草稿至少包含：

- 岗位基本信息和招聘目标。
- 必须条件。
- 加分条件。
- 风险项。
- 评分维度、维度说明和权重。
- 每项内容对应的 Word 原文证据。
- 模型无法确认、需要 HR 补充的问题。

### 5.2 草稿与发布

模型输出永远先进入草稿态。HR 可以新增、删除和修改维度、权重、条件及说明。

发布前必须满足：

- 至少存在一个评分维度。
- 所有维度有名称和判断说明。
- 权重合计为 100%。
- 必须条件和风险项不存在明显自相矛盾。
- HR 明确点击“确认并启用”。

发布后版本不可直接修改。再次编辑会复制成新草稿，重新发布后才成为职位当前标准。没有已发布标准时，评分接口必须拒绝创建正式评分任务，并返回“请先确认评分标准”。

## 6. 简历结构化

### 6.1 输入范围

- 候选人发送并归档的 PDF 简历。
- 从 BOSS 主动寻访归档的 PNG 在线简历。
- 文字型和扫描型 PDF 使用统一处理入口。

### 6.2 统一结构

结构化结果至少包含：

- 基础信息与联系方式。
- 求职方向和当前状态。
- 工作经历。
- 项目经历。
- 教育经历。
- 技能、证书和语言能力。
- 工作年限和可验证的关键成果。
- 无法确认、相互冲突或缺失的字段。
- 重要字段对应的原文证据和页码或图片区域。

模型不得用常识补全缺失经历。无法从原文确认时必须输出空值或“信息不足”。结构化数据与原始简历预览并存，HR 随时可以对照原文。

## 7. 简历评分与建议

### 7.1 前置条件

只有同时满足以下条件才能评分：

- 职位存在已发布且启用的岗位标准版本。
- 简历存在已完成的结构化版本。
- 当前用户存在可用的模型配置。

### 7.2 评分输出

评分结果包含：

- 总分和各维度得分。
- 每项得分所对应的标准。
- 支持该判断的简历原文证据。
- 满足项、不满足项和信息缺失项。
- 模型置信度。
- 需要 HR 核实的问题。
- 筛选建议：建议进一步沟通、建议人工复核、暂不建议推进。

模型没有证据时不得给出确定性判断。评分只生成建议，不自动修改候选人状态、不自动发消息、不自动淘汰。

## 8. 页面与交互

### 8.1 智能初筛工作区

现有简历中心顶部的“智能初筛”卡改为真实工作区：

- 显示岗位标准状态：未上传、解析中、待确认、已启用。
- 显示当前启用版本、文档数量和更新时间。
- 根据状态只展示一个主操作：“上传标准”“确认标准”或“查看标准”。
- 历史版本、重新解析和停用等低频操作放入“…”菜单。

### 8.2 标准编辑抽屉

- 左侧查看 Word 原文与证据位置。
- 右侧编辑评分维度、权重、必须条件和风险项。
- 顶部明确展示草稿或已启用状态。
- 发布前展示权重、空字段和冲突校验结果。

### 8.3 简历列表和详情

列表增加解析状态、评分结果和筛选建议三列。勾选简历后显示浮动批量操作条，可执行重新解析和按当前标准评分。低频单行操作收进“…”菜单。

简历详情抽屉包含：

- 原始简历。
- 结构化信息。
- 评分证据。
- 处理记录。

### 8.4 模型配置

现有招聘 Copilot 配置抽屉增加“测试连接”。未配置或连接失败不影响文件归档，只把相关 AI 任务置为“等待模型配置”。配置恢复后可继续任务。

### 8.5 招聘看板

招聘看板增加待解析简历、待确认标准、待人工复核和建议进一步沟通等汇总。点击汇总项跳转至当前职位对应的筛选结果。看板不直接编辑标准或评分。

## 9. 错误处理与恢复

- 文件读取、文本提取、OCR、模型连接、输出校验和数据保存分别记录失败阶段。
- 模型超时、限流和临时网络错误采用递增等待并限制最大次数。
- API Key 错误、余额不足或模型不支持时停止自动重试并显示明确原因。
- 模型输出必须通过 JSON Schema；格式错误只自动修复一次，仍失败则等待人工重试。
- 已完成的本地提取结果可复用，重新调用模型不重复 OCR。
- 重试使用同一业务幂等键，不生成重复的当前结果。
- 删除或归档原文件前显示关联标准、结构化结果和评分记录的影响。

## 10. 隐私、权限与审计

- API Key 按登录账号加密保存，仅在服务端调用时解密。
- 前端只能看到是否已配置和末四位，不能读取完整 Key。
- 用户只能访问其权限范围内的职位、候选人、文件、任务和结果。
- 模型请求只发送完成任务所需的提取文字，不发送原始文件。
- 应用日志不保存 API Key、完整简历正文或候选人联系方式。
- 审计记录保存操作者、职位、文件版本、标准版本、模型、动作和时间。
- 性别、民族、婚育等敏感属性不进入评分输入和评分维度。

## 11. 测试策略

测试数据全部使用项目生成的虚构候选人和文件，不使用真实公司或候选人资料。

### 11.1 后端测试

- DOCX 段落、表格、证据位置和文件版本。
- DOC 转换可用与不可用两种路径。
- 文字 PDF 提取、扫描 PDF OCR 降级和 PNG OCR。
- 岗位标准草稿、编辑、权重校验、发布和版本不可变性。
- PDF 与 PNG 生成同一结构化 Schema。
- 未发布标准时拒绝评分。
- 评分结果对标准、简历和证据的可追溯性。
- 任务幂等、重试、恢复和历史版本。
- 用户间模型配置、文件和结果的数据隔离。

### 11.2 模型网关测试

使用本地模拟服务覆盖：

- 正常 OpenAI 兼容响应。
- 连接超时、限流、鉴权失败和余额不足。
- 非法 JSON、缺少字段和无证据结论。
- 自动格式修复一次后成功或失败。
- API Key 不出现在响应和日志中。

### 11.3 前端测试

- 岗位标准各状态和唯一主操作。
- 标准编辑、权重校验、发布确认和历史版本。
- 简历解析状态、失败详情和重试。
- 原始简历、结构化信息、评分证据和处理记录切换。
- 批量解析、批量评分和模型未配置状态。
- 看板汇总到筛选列表的跳转。

### 11.4 完整验证

- Django 全量测试。
- Vue 全量测试。
- Vue 生产构建。
- 浏览器验证上传、解析、确认、评分、失败重试和跨职位隔离。

## 12. 验收标准

1. 上传岗位 Word 后，系统能自动提取内容并生成带原文证据的可编辑标准草稿。
2. 没有 HR 发布的评分标准时，任何简历都不会出现正式分数。
3. PDF、扫描 PDF 和 BOSS PNG 在线简历都能进入同一结构化数据模型。
4. 结构化字段和评分结论能定位到原文页码或图片区域；无证据内容显示“信息不足”。
5. 发布标准后，可以对单份或多份简历评分，并展示维度分、证据、置信度和筛选建议。
6. 所有结果都能追溯到职位、原文件版本、标准版本、模型和处理时间。
7. 模型或 OCR 失败时状态清晰、可以恢复，且不会重复产生结果或无上限消耗模型额度。
8. API Key 不离开服务端，不以明文存储，也不出现在页面、响应或日志中。
9. AI 评分不自动淘汰、推进或联系候选人。

## 13. 实施顺序

1. 扩展模型配置测试连接和服务端模型网关。
2. 建立通用 AI 任务、文件提取结果和版本化数据模型。
3. 完成 DOCX、DOC、PDF、扫描 PDF 和 PNG 的本地提取适配器。
4. 完成岗位标准草稿、编辑、发布和版本管理。
5. 完成简历结构化、证据定位和详情展示。
6. 完成评分内核、批量评分、证据和建议展示。
7. 完成招聘看板汇总、异常恢复、全量测试和浏览器验收。
