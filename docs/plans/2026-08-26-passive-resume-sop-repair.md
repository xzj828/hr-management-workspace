# 被动获取简历 SOP 修复

Date: 2026-08-26
Status: completed 2026-08-27

## 问题与证据

- BOSS 沟通页的会话行包含账号内唯一的 `data-id`，但固定版本 CLI 的列表文本只输出姓名、岗位和未读状态，导致项目丢失平台稳定身份。
- 消息同步只会把列表行绑定到已经存在的 `JobApplication`；清理演示数据后真实库中没有应聘记录，因此真实投递消息无法落库、分类或生成求简历确认。
- Worker 已禁止按姓名执行外发动作，但 `BossCliRunner` 尚未实现按会话稳定 ID 打开、复核并执行，已确认的求简历任务仍会转人工。
- 既有同步曾打开真实未读会话但未持久化消息；后续只读未读列表无法自动补回，必须能恢复 Worker 最后选中的已读会话，同时避免把全部历史会话重新激活。

## 选定方案

1. 由项目 Playwright 适配层读取 `.geek-item[data-id]`，输出稳定 ID、姓名、岗位、未读数和消息摘要；CLI 只负责把页面切到相应列表状态。
2. 服务端仅在稳定 ID 存在、岗位能在冻结 scope 内唯一解析时创建或复用 `Candidate`、`CandidateExternalIdentity` 和 `JobApplication`。后续消息与附件回写只使用服务端解析出的 application ID，不信任姓名或 Worker 自报的 application ID。
3. 标准被动流程的首次 `sync_messages` 读取全量列表，但只打开未读行和当前选中行；这能恢复上次失败后仍选中的真实来信，同时不会把全部历史会话重新激活。定时订阅仍只处理未读。
4. `BossCliRunner` 增加按稳定 ID 的会话打开与选中态复核。首次联系在同一动作中先发送已确认话术，再调用 BOSS 原生“求简历”；已有 HR 消息时只执行原生“求简历”。
5. 对方发来 PDF 后，既有未读同步、附件下载、服务端路径校验和归档链路保持不变。

## 安全约束

- 不按姓名、列表序号或组合指纹授权外发；序号只能在同一次稳定 ID 刷新后作为 CLI 定位参数。
- 每次发送前必须重新读取会话列表并验证唯一稳定 ID，打开后再次验证选中会话的 `data-id`。
- 外发仍要求不可变审批快照、额度、幂等和 Plan revision/generation fence；结果不确定时转人工且不自动重试。
- 回填只允许冻结岗位 scope 中的未读或当前选中会话；缺少稳定 ID、岗位歧义、同名冲突或 scope 已变化的行不得建档或打开。

## 验证

- Playwright 会话稳定 ID 抽取与选中态复核单测。
- CLI 列表增强和按稳定 ID 首联复合动作单测。
- Worker 已读回填、未读轮询和同名安全失败单测。
- Worker API 从零创建真实候选人/应聘、消息分类、确认草稿和附件归档测试。
- Django 聚焦回归、系统检查、真实受管浏览器只读验证；部署后不自动批准或发送外部消息。

## 完成结果

- 真实受管 BOSS 页面只读验证：目标岗位 26 条会话全部具备唯一稳定 ID，且有 1 条目标岗位当前选中会话可安全恢复。
- 对抗审查修正了 Playwright 过时读取 API、严格姓名复核和外部结果不确定时的禁止重试边界；最终四维评分均不低于 8/10。
- Django system check、迁移检查、招聘全量 442 项测试，以及新增 PDF 归档等聚焦用例通过。
- 未在验收中批准或执行真实外发；首次真实发送仍由 HR 在工作台确认最终话术。

## 运行时补充修复（2026-08-27）

真实运行验证发现：周期消息同步可以创建候选人、应聘和求简历审批，但招聘作业台没有读取异步生成的审批；停止方案后旧代审批会按安全边界作废，已处理消息又不会在新代自动恢复，造成“已识别来信但没有发送”的表象。

补充契约如下：

1. 招聘作业台在运行被动方案时，按当前岗位、方案修订和代际轮询 `draft/request_resume` 审批，并内联展示候选人、最终话术、到期时间与明确确认按钮。
2. HR 点击确认后才物化执行批次；Worker 继续按稳定会话 ID 重新定位和复核，在首次联系时先发送已确认话术，再调用 BOSS 原生“求简历”。
3. 每次有效的周期消息同步完成后，服务端恢复当前岗位中“已有候选人来信、尚无简历、且没有有效求简历动作”的记录。旧代已拒绝、已过期或已取消审批允许在新代重新生成；成功、排队、运行中、等待人工或结果不确定的动作不得自动重建。
4. 恢复操作按 `application + source message + plan revision + generation` 幂等；停止或换代后旧 fence 不得创建新审批，已有简历不得再次求取。

### 补充修复验收结果

- 招聘后端全量 445 项、前端全量 248 项测试通过；Django system check、迁移漂移检查、生产构建与 `git diff --check` 通过。
- 真实本地数据库只读 API 验证：审批筛选返回 200 且包含方案修订/代际字段；停止状态下恢复函数返回 0，未创建新审批。
- 单会话对抗审查额外修复了岗位停止、切换或组件卸载时旧审批请求晚返回的竞态；最终四维评分为 9/8/8/8，结论 PASS。
- 验收未批准真实审批、未向候选人发送消息、未点击 BOSS“求简历”。
