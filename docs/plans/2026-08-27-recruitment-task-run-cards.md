# 招聘任务按单次执行持久展示

日期：2026-08-27  
状态：已完成

## 问题

- 招聘任务集合当前按岗位级 `RecruitmentAutomationPlan` 渲染；同一岗位反复执行只更新 `current_revision/current_run`，因此多次执行最终仍只有一张卡。
- 用户心智中的“任务”是每次点击开始后产生的一次运行；只要没有显式删除，该次任务卡就应持续存在。
- 现有删除动作归档整个 Plan，不能表达只隐藏某一次历史运行。

## 设计决策

1. 保留“每岗位一个 Plan”的控制面和唯一约束，继续负责停止栅栏、不可变修订、控制代际和当前运行。
2. 招聘任务集合改以正式、Plan 管理的 `WorkflowRun` 为卡片身份；每次执行产生一张独立卡片，历史运行不会被后续执行覆盖。
3. `WorkflowRun.archived_at` 只控制该次任务卡的可见性，不物理删除 Plan、Revision、Run、节点、结果或审计证据。
4. 当前任务沿用 Plan 的有效状态并允许控制；历史任务只读展示自己的修订、运行状态和业务结果，不得控制或覆盖当前 Plan。
5. 单次任务仅在运行终态时允许删除；恢复只清除 `archived_at`，不会重启任务。

## 交互

- `/recruitment/tasks` 默认返回并展示全部未删除的正式 Plan Run；搜索、状态和类型筛选对每张运行卡生效。
- 卡片显示岗位、该次方案类型、方案版本、运行编号、真实状态和该次更新时间。
- 卡片继续进入现有任务详情子页面，并通过 `run` 查询参数固定历史运行上下文。
- 当前运行显示停止、修改、重新开启等 Plan 控制；历史运行仅提供查看结果和删除/恢复。

## 验收标准

- [x] 同一岗位连续执行 N 次后，任务集合出现 N 张卡，刷新和后续执行不会覆盖旧卡。
- [x] 未删除的历史任务持续可见；删除一张卡不影响其他卡、Plan、Revision、结果或审计证据。
- [x] 历史卡进入详情后显示自己的版本、运行编号、状态和结果，不显示当前 Plan 的控制按钮。
- [x] 当前运行仍可停止、修改、重新开启，自动化安全边界不变。
- [x] 后端专项测试、前端专项 Vitest 和生产构建通过。
