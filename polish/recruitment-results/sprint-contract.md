# Sprint Contract：结果中心方案 C

## Baseline

- 总分：15/20
- 最差维度：Visual Craft / Coherence（3）
- 当前截图：`../final-results.png`
- 用户参考：`reference-c-selected.png`

## Gap 分析

### Compliance

- [ ] 删除页面级与区块级重复英文 kicker，仅保留中文业务层级。
- [ ] 视觉色值继续集中在 `--results-*` token；主色、暖白表面、墨色、弱文字、边框、警告和危险色均映射 `DESIGN.md`。
- [ ] 控件 9px、主面板 15px、状态胶囊圆角；普通表面阴影不得超过标准面板阴影。
- [ ] 常规业务文字 12–13px，辅助文字不小于 10px，KPI 使用系统无衬线。

### Craft

- [ ] 1660px 页面容器内，筛选栏为单行三列，列宽约 1.2fr / 1fr / 0.65fr；720px 以下才纵向堆叠。
- [ ] KPI 与筛选共享连续表面，四列等高；上下区之间仅使用 1px 分割线。
- [ ] 四个 Tab 在桌面保持单行等分；激活态为 2px 青绿下划线和文字强调，不再触发 2×2 布局。
- [ ] 人工事项使用六列队列表达，行高约 58–64px；手机端再降为纵向内容。
- [ ] 任务结果保持双列，运行/寻访行使用分割线和 5px 进度条，避免逐项悬浮卡片。
- [ ] 候选表格保持连续排名，表头、选中行、状态、操作列稳定对齐；仅表格容器允许横向滚动。
- [ ] 招聘进度使用横向阶段分布：每阶段显示名称、数量、占比和色条；下方显示招聘目标、候选总数、在招人数与完成度。
- [ ] 空态最大高度受控，不能再次出现占据大半屏的无效留白。

### Coherence

- [ ] 四个视图统一使用“中文标题行 → 数据头/筛选 → 分割行内容”的同一种视觉语法。
- [ ] 成功、警告、危险、处理中状态使用同一组淡色标签且始终带文字。
- [ ] 桌面端、1050px、720px 三档布局保持相同层级，不让响应式规则改变桌面视觉意图。

### 前后端数据适配

- [ ] 所有数字来自现有真实接口：`workflow-runs`、`search-campaigns`、`human-attentions`、`screening-results`。
- [ ] 招聘阶段统计由 `screening-results.application.stage` 与共享 `stageColumns` 计算，不写死参考图数字。
- [ ] 后端字段若已完整则不制造重复聚合端点；若发现真实数据缺口，补 serializer/view/tests 后再接入。
- [ ] Loading / Empty / Partial Error / Fatal Error 均保留且不展示伪造数据。

## 验收标准

1. 1720×1000 真实页面截图在整体节奏、连续筛选/KPI、单行 Tab、暖白/青绿层级上匹配方案 C。
2. “需要人工、任务结果、候选人与简历、招聘进度”四个真实 Tab 均完成截图验收。
3. 页面无横向溢出；候选表仅局部滚动；720px 下控件触达尺寸不低于 44px。
4. 前端结果中心定向 Vitest 全部通过；前端 build 通过。
5. 若改动后端，则对应 Django 定向测试通过；若无需改后端，记录现有契约已满足方案 C。
6. 浏览器控制台无新增 error，四个 Tab、筛选、刷新与可见动作均可操作。

## PASS 阈值

- 总分 ≥16/20，且无单项 ≤2。
- Functionality 必须为 5。
- 方案 C 的四个核心特征（单行筛选、单行 Tab、暖白连续表面、横向阶段分布）缺一即不通过。

## 改动边界

- 允许：`RecruitmentResultsView.vue` 的语义展示结构、样式 token、响应式规则与由现有响应数据计算的展示摘要。
- 条件允许：仅在真实字段缺失时修改 recruitment serializer/view 与定向测试。
- 禁止：改变审批、外发通知、人工确认、运行控制、候选人结论、路由恢复和权限逻辑。
